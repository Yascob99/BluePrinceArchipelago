# Archipelago

## General Info

These are the core functionality and supportive classes for interacting with the archipelago server and creating the client. A lot of the server interaction is handled through the [Archipelago.MultiClient.Net](https://github.com/ArchipelagoMW/Archipelago.MultiClient.Net) Api.

## Archipelago Client

This Class contains the majority of the code for Connecting, Reconnecting, Disconnecting to the Archipelago Server. It also handles sending and recieving important server packets such as Messages, Errors, Items, SocketClosed, and Locations being manually checked by the server.

In addition the following is also handled here:
* Rebuilding the local state based on a combination of locally stored data and server data on reconnect.
* Figuring out if the item received should be handled immediately or delayed for later.

### Archipelago QueueManager

This Class handles my custom Queue like lists for queueing specific types of data. The reason lists were used at this time was because queues were running into threadedness issues for some reason. I could probably rework all this to try again with queues but haven't gotten to that yet.

## Archipelago Console

This class handles displaying the UI and the underlying code for the in game console added by the mod as well as any related logging functions.

### Commands

Commands are custom made local commands meant to run code when invoked in the client console.

#### Command Manager

This manages and registers all commands and handles parsing of messages into a command and it's args. ParsedCommand is a class that helps organize the data of the Command and Args into one convenient object.

#### Command

Command defines an abstract class for how commands should be structured. It accepts a name and the abstract fields "Description", and "Syntax". Additionally it has an abstract function "Run" which accepts a list of args as it's parameter.

How the command is processed from there is fully up to the creator of the command.

Currently there is no function to wait on a user response, but this functionality may be added later.

## Archipelago Data

This class is intended to keep a list of core data related to the current archipelago session. Mainly this stores raw data from connection or processed data such as dicts for looking up server data. Some of the data is reconstructed from the locally saved session data instead on reconnect as that can be more accurate in certain cases such as the location dict.

## Archipelago Options

This class is meant to store static references to the SlotData received from Archipelago as well as handle the processing of that data when converting from the raw json. It will need to be updated alongside the SlotData model anytime new options and data is added to the slot_data generated by the apworld and served to the mod/client on connecting to Archipelago data.

## DeathLink Handler

This class handles all functionality related to DeathLinks. This includes processing detecting when a DeathLink should be sent, Receiving remote DeathLinks, sending DeathLink messages, and handling any local changes to DeathLink Options.

## DeathLink Messages

This class stores and handles which DeathLink messages are enabled based on the local DeathLink Settings.
